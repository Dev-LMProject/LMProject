# 검토 후 단계별 개발 안내

기능 설계를 독립 검토한 뒤 사용자가 직접 구현하도록 안내한다. 현재 프로젝트 지침과 실제 코드가 기준이며 사용자의 언어로 설명한다. 상대 링크는 이 스킬 폴더 기준이다.

## 먼저 요청을 분기한다

| 요청 | 이번에 수행할 범위 |
| --- | --- |
| 새 기능 설계, 요구·공개 인터페이스·상태 소유권 변경 | [설계 검토](references/design-review.md)를 읽고 영향 범위를 설계·검토한다. |
| `다음 단계`, 특정 단위 설명 | 기록과 해당 소스를 대조한 뒤 아래 단위 안내로 간다. 해당 계약의 검토 완료 근거가 없거나 계약이 달라졌으면 설계 검토로 돌아간다. |
| `적용했어`, 적용 확인 | 해당 단위의 diff·연결·확인 가능한 결과를 점검하고 적용·검증 상태를 갱신한다. |
| `이 단계 구현해줘` | 명시된 단위만 프로젝트의 구현·검증 절차로 수행한다. |
| 이 스킬 자체의 분석·수정 | 스킬 파일과 참조를 수정 대상으로 다룬다. 기능 설계의 세 역할 검토를 재귀 실행하지 않는다. |

**기본 권한은 조사·설계·검토·개인 기록·예시 작성이다. 소스·애셋·설정 변경은 사용자가 별도로 구현을 요청한 범위에 한한다.** 설계만을 위한 작업 트리·커밋·PR·배포는 시작하지 않는다. 기존 승인과 결정을 유지하며, 설명 요청·시간 경과·자동 계속 알림을 구현 승인으로 해석하지 않는다.

## 필요한 근거만 읽는다

- 먼저 프로젝트 지침에 따라 해당 작업 기록을 복구한다. 이후 현재 단위와 변경 범위에 필요한 소스·호출부·설정·애셋·미커밋 변경을 확인하고, 판단에 필요한 연결을 따라 조사 범위를 넓힌다.
- 같은 문맥에 있고 변경되지 않은 문서·소스는 다시 읽지 않는다. 재개·압축·외부 변경 때는 기록의 소스 기준과 실제 상태를 대조한다. 접근할 수 없는 자료는 미확인으로 남긴다.
- 하위 스킬과 참조는 현재 분기에 필요한 것만 읽는다. 단위 안내·적용 확인에는 초기 설계 검토의 스킬 묶음과 검토자를 다시 불러오지 않는다.

UE 5.8+ 설계·검토·예시에는 다음을 공통 적용한다.

- UObject의 생성·소유·GC·해제 시점을 확인한다. GC가 추적할 멤버는 `UPROPERTY()`와 `TObjectPtr<T>`, 수명을 유지하지 않는 참조는 필요에 따라 `TWeakObjectPtr<T>`를 사용한다. 일반 C++ 포인터에는 강제하지 않는다.
- 리플렉션 타입의 `GENERATED_BODY()`와 해당 `*.generated.h`를 확인하고 generated 헤더를 마지막 include로 둔다.
- 전방 선언으로 충분하면 헤더 include를 줄이고 구현용 include는 `.cpp`로 옮긴다. 완전한 타입 정의·UHT에 필요한 include는 실제 프로젝트 엔진 버전 기준으로 유지한다.

## 기록과 전체 개요

조정자 한 명이 저장소의 개인 기록 방식에 맞춰 **최신 설계 하나**와 다음 상태를 관리한다. 별도 방식이 없으면 작업별 비공유 기록 하나를 사용한다. 저장이 불가능하면 대화에 기록하고 한계를 알린다.

- 확정 요구·결정 이유, 자료 접근 범위와 소스 기준(관련 미커밋 변경 포함), 설계 버전.
- 실제 검토 방식·독립성·역할별 판정, 지적 ID별 처리 근거와 미해결 사항.
- 순서 있는 개발 단위·선행 조건·완료 기준, 개요를 제시한 버전, 마지막 설명 단위, 사용자 적용 여부, 검증 범위·결과.

결정·설계·검증·진행 상태가 바뀔 때 해당 항목만 갱신한다. 전체 소스·리뷰 전문·같은 설계를 기록마다 복제하지 않는다. 저장소가 정한 기록 파일 수와 복구 규칙을 따른다.

검토가 끝나면 **모든 개발 단위의 번호·이름·목표·완료 기준·선행 관계를 먼저 제시**하고 검토 결과·미실행 검증·다음 단위를 알린다. 개요에는 구현 코드나 세부 노드 연결을 넣지 않는다. 한 단위는 목적 하나와 확인 가능한 변화 하나로 구성하며 필요한 호출부·선행 타입·테스트 설정을 포함한다.

이미 요청받은 단위가 있으면 같은 응답에서 이어 설명한다. 없으면 요청을 기다린다. 개요가 누락됐거나 단위 구성이 바뀌었을 때 갱신하며, 그대로인 전체 개요를 매번 재출력하지 않는다.

## 요청받은 단위 하나 안내

해당 단위의 현재 소스와 선행 작업을 확인한다. 누락된 선행 작업은 위치와 보완 방법을 알리고, 뒤 단계 없이 확인할 수 없는 순서는 조정한다. 임시 반환·미연결 부분은 이유와 현재 가능한 동작을 명시한다.

1. **목표**: 이번에 달라질 동작과 범위.
2. **구조와 이유**: 기존 호출 흐름에서 바꿀 부분과 이유.
3. **따라 할 작업**: 정확한 파일·심벌 또는 애셋·노드 위치, 추가·교체·삭제 순서, 필요한 코드와 연결. 프로젝트 코드 형식을 지키고 실제 적용할 수 있을 만큼 구체적으로 쓴다.
4. **확인 방법**: 선행 설정, 입력 순서, 기대 결과, 후속 단위에 남는 동작. 정적 확인과 빌드·실행 검증을 구분한다.
5. **종료 상태**: 설명·적용·검증 중 확인된 상태와 다음 단위 이름.

사용자가 검증을 맡았다면 절차와 기대 결과만 제공한다. 예시 전달은 적용·테스트 완료가 아니다. 설명에 필요한 코드를 토큰 절약을 이유로 생략하지 않는다.

요구나 코드 차이로 검토된 계약이 바뀌면 영향받는 부분을 다시 검토한다. 단순 위치·표기 변경은 참조와 기록을 갱신한다. 사용자 입력 대기 중 반복 조회·재검토를 하지 않으며, 설계 통과나 설명 대기를 실제 기능 구현 완료로 처리하지 않는다.
