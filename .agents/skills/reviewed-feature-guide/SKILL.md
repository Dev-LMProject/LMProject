# 검토 후 단계별 개발 안내

기능 설계를 교차 검토한 뒤 사용자가 직접 구현하도록 안내한다. 현재 프로젝트의 지침과 실제 코드가 기준이다. 설명은 사용자의 언어로 작성한다.

운영체제, 셸, 특정 모델이나 도구 이름에 의존하지 않는 지침이다. 이 스킬의 상대 링크는 현재 작업 폴더가 아니라 이 `SKILL.md`가 있는 폴더를 기준으로 읽는다. `agents/openai.yaml`은 지원하는 호스트의 선택적 표시 정보다.

## 작업 권한과 진행 신호

기본 작업은 읽기 조사, 설계, 검토, 개인 진행 기록, 따라 쓸 예시 작성이다. **실제 소스·애셋·설정 변경은 사용자가 별도로 구현을 요청한 범위에서만 수행한다.** 설계만을 위해 작업 트리 생성, 커밋, PR, 배포를 시작하지 않는다.

| 입력 | 수행할 일 |
| --- | --- |
| 새 기능 설계 요청 | 아래 검토 절차를 끝낸 뒤 전체 개발 단위 개요와 준비 상태를 알린다. |
| `다음 단계`, `1단계 설명해줘` | 해당 개발 단위 하나만 안내한다. 구현 승인이 아니다. |
| `적용했어`, 확인 요청 | 해당 단위의 현재 변경과 확인 가능한 결과를 점검한다. |
| `이 단계 구현해줘` | 명시된 단위만 구현한다. 프로젝트의 구현·검증 규칙을 적용한다. |
| 자동 목표 계속 알림, 시간 경과 | 다음 설명이나 구현의 승인으로 해석하지 않는다. |

이미 받은 결정과 승인은 유지한다. 모호한 말은 대화 맥락으로 해석하되 구현으로 범위가 넓어지는 경우에만 짧게 확인한다. 도구가 실제 제공하는 권한과 상위 지침을 따른다.

## UE 5.8+ 코드 기준

UE 5.8 이상 프로젝트에서는 설계·구현·예시 코드와 세 검토 역할에 다음 기준을 공통 적용한다.

- **UObject 생명주기 및 TObjectPtr 규칙 준수:** 생성·소유·GC·해제 시점을 확인한다. GC가 추적해야 하는 UObject 멤버 참조에는 `UPROPERTY()`와 `TObjectPtr<T>`를 사용하고, 수명을 유지하지 않는 참조는 필요에 따라 `TWeakObjectPtr<T>`를 사용한다. 일반 C++ 구조체·클래스 포인터에 UObject 포인터 규칙을 강제로 적용하지 않는다.
- **헤더의 GENERATED_BODY() 준수:** 리플렉션 타입에는 필요한 `GENERATED_BODY()`와 해당 `*.generated.h`를 포함하며, `*.generated.h`는 헤더의 마지막 include로 둔다.
- **헤더 include 최소화:** 전방 선언으로 충분한 타입은 전방 선언하고 구현에만 필요한 include는 `.cpp`로 옮긴다. 상속·값 타입 멤버 등 완전한 정의가 필요한 include는 유지한다. 실제 프로젝트 엔진 버전의 API와 UHT 요구사항을 기준으로 확인한다.

## 1. 현재 상태와 검토 방식 확인

1. 접근 가능한 저장소 지침, 관련 소스와 호출부, 설정·애셋·기존 검증 자료, 미커밋 변경을 읽는다. 파일 접근이 없으면 사용자가 제공한 자료로 범위를 제한하고 실제 저장소를 확인했다고 표현하지 않는다. 기존 기능, 임시 구현, 제안을 구분한다.
2. 요구 동작, 성공·실패·취소 경로, 책임과 상태 소유자, 영향받는 호출부, 필요한 검증을 짧게 정리한다. 결정에 필요한 정보만 사용자에게 묻고 독립적인 조사는 계속한다.
3. 현재 스킬 목록에서 다음 역할의 실제 지침을 찾아 읽는다. 호스트에 따라 접두사가 없거나 이름이 달라도 제공자·내용을 확인해 대응시킨다. 설치 버전이나 머신 경로를 고정하지 않는다.
   - `mattpocock-skills:codebase-design`: 인터페이스와 책임 경계, 복잡도 은닉, 최종 설계 검증.
   - `superpowers:brainstorming`, `superpowers:writing-plans`: 설계와 개발 단위 구성.
   - `ponytail:ponytail`: 리뷰 역할에 **Ultra** 수준을 지정해 요구에 비해 과한 구조와 더 작은 완전한 해법을 검토.
4. 이 흐름에서 하위 스킬의 자동 구현·커밋 단계는 실행하지 않는다. 코드 변경 전용 리뷰를 설계 검토인 것처럼 표시하지 않는다.

지정 스킬과 독립 검토자를 사용할 수 있으면 **원본 검토**를 진행한다. 자동 서브에이전트가 없거나 지정 스킬이 누락됐거나 사용자가 대체 검토를 요청하면 [대체·수동 검토 안내](references/portable-review.md)를 읽는다. 가능한 조사·초안은 계속하되, 대체 방식과 독립성의 차이를 설명하고 사용자가 선택한 범위에서 진행한다. 이미 명시한 선택은 다시 묻지 않는다. 스킬이나 플러그인을 자동 설치하지 않으며, 실제로 수행하지 않은 named 역할의 검토를 완료로 기록하지 않는다.

완료 조건: 확인된 요구, 자료 접근 범위, 미확정 결정, 선택한 원본·대체 검토 방식과 검토자 실행 방법이 구분되어 있다.

## 2. 서브에이전트 검토와 수정 반복

세 역할을 분리한다. 호스트가 지원하면 같은 역할의 에이전트를 다음 회차에 재사용하고, 재사용할 수 없으면 최신 인계 자료로 교체한다. 의존하는 회차를 병렬로 실행하지 않는다. 서브에이전트와 수동 검토자에게 설계·검토만 수행하도록 지시한다. 아래 이름은 원본 검토의 역할이며 대체 검토에서는 참조 문서의 일반 역할 이름을 사용한다.

사용 중인 `brainstorming`에 Builder check 지침이 있으면 첫 Ultra 검토자에게 함께 전달한다. 이 독립 검토자가 설계만으로 계획을 만들 때 잘못 추측하게 될 미확정 질문과 이유를 확인하고, 구현자에게 위임된 결정과 취향은 제외한다. 같은 검토를 위해 별도 에이전트를 만들지 않는다.

| 역할 | 읽을 것과 산출물 |
| --- | --- |
| Superpowers 설계자 | 요구와 실제 코드를 바탕으로 책임 분리, 공개 인터페이스, 상태·호출 흐름, 예외 경로, 개발 단위와 검증 순서를 설계한다. |
| Ponytail Ultra 검토자 | 같은 설계 버전과 연결 코드를 읽고 정확성, 생명주기, 취소·재진입, 호출부·설정 누락, 불필요한 추상화를 검토한다. 필수 요구나 안전한 오류 처리를 단순화를 이유로 제거하지 않는다. |
| mattpocock 최종 검증자 | 수정된 최신 설계 전체와 지적 처리 근거를 읽고 요구 충족, 모듈 경계, 변경 파급, 따라 할 단계의 완결성을 판정한다. |

각 에이전트에 요구사항·사용자 결정, 소스 근거, 설계 버전, 검토 범위, 구현 금지를 전달한다. 검토자는 이전 리뷰어의 결론을 승인 근거로 삼지 않고 직접 확인한다.

반복 순서:

1. Superpowers 설계자가 버전을 붙인 설계를 작성한다.
2. Ultra 검토자가 지적마다 `ID / 중요도 / 발생 조건과 근거 / 최소 수정안`을 낸다.
3. 지적을 설계자에게 돌려보낸다. 설계자는 반영하거나 근거를 들어 기각하고 변경 이유를 기록한다. 동작·요구·프로젝트 규칙에 영향 없는 취향 제안은 선택 사항으로 분리한다.
4. Ultra 검토자가 수정된 버전에서 지적 해소와 변경 영향을 확인한다. 지적이 남으면 3으로 돌아간다.
5. mattpocock 검증자가 **같은 최신 버전**을 검토한다. 조치할 문제가 있으면 설계자에게 전달하고 3부터 반복한다.

원본 검토 완료 조건: 최신 버전에서 실제 Ultra와 mattpocock 검증이 끝났고, 근거 있는 필수 수정 사항이 모두 해소되었으며 mattpocock이 `남은 설계 수정 사항 없음`으로 판정했다. 대체 검토는 [별도의 완료 조건과 결과 표시](references/portable-review.md)를 적용한다. 이전 버전의 통과 판정은 재사용하지 않는다. 정적 설계 검토를 실행 결과나 무결함 보증으로 표현하지 않는다.

판단에 필요한 정보가 없거나 같은 쟁점이 근거 추가 없이 반복되면 그 미해결 사항과 필요한 입력을 보고한다. 횟수 제한에 도달했다는 이유로 통과시키거나, 취향만 바꾸며 검토를 반복하지 않는다.

## 3. 개발 단위와 진행 기록

저장소의 개인 작업 기록 방식을 우선 사용한다. 없으면 쓰기가 허용된 작업별 비공유 위치에 간결한 기록 하나를 둔다. 파일 저장을 할 수 없으면 아래 항목을 복사 가능한 대화 내 진행 기록으로 제공하고 디스크에 저장했다고 주장하지 않는다. 기록 소유자는 조정자 한 명이며, 검토자는 결과를 전달한다.

기록할 내용:

- 확정된 요구와 결정 이유, 자료 접근 범위, 소스 기준, 검토 방식·독립성, 설계 버전과 각 역할의 실제 검토 결과.
- 지적 ID별 반영·기각 근거와 미해결 사항.
- 순서가 있는 개발 단위, 각 단위의 선행 조건과 완료 기준, 전체 개요를 제시한 여부와 기준 설계 버전.
- 마지막으로 **설명한 단위**, 사용자 **적용 여부**, **검증 범위와 결과**를 각각 기록한 진행 상태.

단위 수는 기능에 맞춘다. 한 단위는 목적 하나와 확인 가능한 변화 하나로 구성하고, 호출부·선행 타입·필수 테스트용 설정을 포함한다. 뒤 단계의 타입이나 UI가 있어야만 앞 단계를 확인할 수 있는 순서는 수정한다. 중간에 임시 반환이나 미연결 부분이 필요하면 이유와 현재 가능한 동작을 명시한다.

설계 검토가 끝나면 **전체 개발 단위 개요를 먼저 제시**한다. 표나 번호 목록으로 모든 단위의 번호·이름·목표·완료 기준과 필요한 선행 관계를 짧게 보여주고, 검토 결과·미실행 검증·다음에 안내할 단위를 알린다. 개요에는 구현 코드나 세부 노드 연결을 넣지 않는다.

그다음 사용자가 요청한 단위 하나씩 4절에 따라 상세히 설명한다. 이미 특정 단위를 요청했다면 전체 개요를 먼저 보여준 뒤 같은 응답에서 해당 단위를 설명하고 재요청을 요구하지 않는다. 아직 단위를 요청하지 않았다면 개요를 제시한 뒤 기다린다. 진행 중 전체 개요가 누락되었거나 단위 구성이 바뀌면 다음 상세 설명 전에 개요를 제시하거나 갱신한다.

## 4. 요청받은 단위 하나 설명

매 요청에서 기록과 접근 가능한 최신 소스를 대조한다. 자료가 없거나 오래됐으면 그 한계를 표시하고 필요한 부분만 요청한다. 파일·심벌이 바뀌었으면 현재 위치를 기준으로 설명한다. 선행 작업 누락은 정확한 위치와 보완 방법을 안내하고, 이미 받은 요청을 이유 없이 다시 받지 않는다. 서로 다른 여러 단위의 내용을 한 답변에 몰아넣지는 않는다.

한 단위를 다음 순서로 설명한다:

1. **이번 목표**: 끝났을 때 달라지는 동작과 다루는 범위.
2. **현재 구조와 이유**: 기존 호출 흐름에서 무엇을 왜 바꾸는지.
3. **따라 할 작업**: 정확한 파일·클래스·함수 또는 애셋·노드 위치, 추가·교체·삭제 순서, 필요한 코드와 연결 순서. 사용자가 적용할 수 있을 만큼 구체적으로 작성하고 프로젝트 코드 형식을 지킨다.
4. **확인 방법**: 먼저 필요한 설정, 입력 순서, 기대 결과, 아직 다음 단계에 남아 있는 동작. 소스 확인과 빌드·실행 검증을 구분한다.
5. **단계 종료 상태**: 설명·적용·검증 중 무엇이 확인되었는지, 다음 단위의 이름만 짧게 남긴다.

사용자가 검증을 맡았다면 검증 절차와 기대 결과를 주고 직접 실행하지 않는다. 코드 예시를 전달했다는 이유로 적용·테스트 완료로 기록하지 않는다.

요구 변경이나 실제 코드 차이로 검토된 계약이 달라지면 영향받는 부분을 다시 설계·검토한 뒤 최신 버전을 최종 검증한다. 단순 파일 위치 변경이나 이미 해결된 쟁점 때문에 전체 검토를 처음부터 반복하지 않는다.

사용자 입력을 기다리는 동안 반복 조회·재검토·같은 상태 보고를 계속하지 않는다. 목표 상태 도구가 있다면 호스트의 완료·차단·일시정지 규칙을 따른다. 설명 대기나 설계 통과를 실제 기능 구현 완료로 처리하지 않는다.
