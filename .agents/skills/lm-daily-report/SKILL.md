# LMProject 일일보고

사용자의 기존 보고 형식을 유지하면서 해당 보고의 집계 기간에 실제로 한 일을 정리한다. 현재 요청에서 정한 범위와 표현이 이 스킬의 기본값보다 우선한다.

## 자료와 문체

- 작성 전에 같은 저장소에 있는 [korean-writing-care](../korean-writing-care/SKILL.md) 스킬을 함께 읽는다.
- 아래 문체 기준은 [im-not-ai의 humanize-korean](https://github.com/epoko77-ai/im-not-ai/blob/main/codex/skills/humanize-korean/SKILL.md)과 [Quick Rules](https://github.com/epoko77-ai/im-not-ai/blob/main/skills/humanize-korean/references/quick-rules.md)를 일일보고에 맞춰 적용한 것이다. 사실·수치·날짜·고유명사·기술 식별자·부정·조건·확정 정도를 보존하고, 번역투·과장·추상적인 평가·불필요한 접속어만 덜어낸다. 기존의 담백한 `했다` 말투를 따른다.
- 사용자가 준 집계 기간의 기록과 확인 가능한 작업 근거를 사용한다. 설계, 구현, 코드 반영, 에디터 확인, 실제 플레이 검증을 서로 구분한다. 이미 다른 보고에 반영한 작업을 중복해서 넣지 않는다.
- 짧은 제목과 목록은 이 보고의 의도된 형식이다. 윤문하면서 산문으로 풀거나 문장 길이와 종결어미를 억지로 다양하게 만들지 않는다. 원문 대비 변경률이나 AI 탐지 점수를 작성 기준으로 삼지 않는다.

## 보고에서 제외할 내용

- 단순한 PR 승인(Approve, 승인 시각, 승인 처리 사실)은 `주요 변화`와 상세 본문에 기록하지 않는다. 승인만으로 코드 검토를 수행했다고 표현하지 않는다.
- 모든 병합 내용(PR 병합, 브랜치 간 병합, `dev` 또는 `origin/dev`를 작업 브랜치에 병합한 내용 포함)은 일일보고의 제목, `주요 변화`, 상세 본문에 기록하지 않는다. 병합 방향이나 대상 브랜치와 관계없이 적용한다.
- 실제 개발·설계·검증과 문제 발견·수정 제안 등 구체적인 내용이 있는 코드 검토는 근거가 있으면 기록한다. 병합 행위와 별개로 확인되는 실제 작업은 기록하되, 병합 자체를 개발 성과로 적지 않는다.
- 기존 보고를 정리할 때는 사용자가 요청한 범위에서 단순 PR 승인 표현과 병합 내용만 최소한으로 삭제한다. 같은 문단의 실제 개발·코드 검토 내용과 그 밖의 수동 작성 내용은 보존한다.

## 집계 기간과 기준시간

현재 기준시간은 **17:40**, 시간대는 **Asia/Seoul**이다. 기준시간은 변경 가능한 설정값이며, 아래의 모든 `기준시간`은 이 값을 따른다. 사용자가 변경을 요청하면 설정값과 적용할 보고 범위를 갱신하며, 과거 보고를 요청 없이 일괄 재분류하지 않는다. 적용 시작 보고가 불명확하면 확인한다. 기준시간이 바뀌는 첫 집계 구간은 이전 기준으로 끝난 직전 구간의 마감 시각 초과부터 새 기준의 마감 시각 이하까지로 잡아 누락과 중복을 막는다.

- 일반적인 업무일 보고에는 **전날 기준시간 초과부터 보고 대상일 기준시간 이하까지** 수행한 작업을 넣는다. 경계 시각의 작업은 마감하는 쪽 보고에 한 번만 포함한다.
- 토요일·일요일에 수행한 작업은 **바로 다음 업무일의 일일보고**에 포함한다. 주말 다음 업무일 보고는 직전 업무일 기준시간 초과부터 해당 업무일 기준시간 이하까지 연속으로 집계한다. 다음 업무일이 월요일이면 금요일 기준시간 이후 작업과 토·일 작업을 월요일 기준시간까지의 작업과 함께 넣는다.
- 토·일 외의 공휴일·개인 휴무 처리 규칙은 임의로 만들지 않는다. 다음 업무일을 정하는 데 필요한 일정이 불명확하면 그 날짜만 확인한다.
- 기준시간 이후 발생한 작업은 방금 마감한 보고에 추가하지 않고 다음 보고 대상 업무일에 배정한다. 마감 전 작성·갱신에서는 해당 집계 기간 중 현재까지 확인된 작업만 반영한다.
- 대화·커밋·에디터 작업·검증 각각의 실제 수행 시각을 근거로 분류한다. 구현 뒤에 생성된 커밋의 시각만으로 구현 시점을 바꾸거나, 범위 밖의 커밋·검증을 범위 안에서 완료한 것으로 쓰지 않는다.
- `기간` 속성에는 집계 시작일이 아니라 **보고 대상일**을 유지한다. 주말 작업을 포함하더라도 같은 날짜 보고의 제목 번호를 바꾸거나 별도 주말 보고를 자동 생성하지 않는다.

## 제목과 날짜

제목은 `[W{주차}-{NN}] {작성자} 일일보고` 형식이다. 작성자는 사용자가 지정한 사람을 우선하고, 기존 보고 수정이면 해당 보고의 작성자를 유지한다. 새 보고에서는 현재 사용자가 누구인지 확인된 대화 맥락과 해당 사용자의 기존 보고를 사용한다. 작성자를 특정할 수 없으면 본문 초안을 준비하고 이름만 확인한다. 다른 팀원의 이름이나 로컬 PC 계정명을 대신 사용하지 않는다. 날짜는 사용자가 지정한 보고 대상일을 쓰고, `오늘`은 Asia/Seoul 기준으로 해석한다.

1. 같은 작성자의 해당 주차 보고에서 마지막으로 작성한 보고의 번호를 확인한다. `W{주차}`는 기존 보고와 프로젝트의 주차 기준을 따른다. 월별 주차나 ISO 주차로 임의 환산하지 않는다.
2. 해당 주차의 첫 보고는 `01`, 이후 새 보고는 마지막 번호에 1을 더해 최소 두 자리로 쓴다. 숫자는 요일 번호가 아니라 실제 보고 작성 순서다.
3. 휴무·공휴일·미작성일은 번호를 소비하지 않는다. 월요일 `W1-01`, 화요일 휴무라면 수요일은 `W1-02`다. 새 주차의 첫 보고는 그 주의 수요일이어도 `W2-01`이다.
4. 같은 날짜의 기존 보고를 수정할 때는 제목 번호를 유지한다. 과거 보고의 번호를 요청 없이 일괄 변경하지 않는다.
5. 주차나 직전 번호를 확인할 수 없으면 요일로 추정하지 않는다. 본문 초안을 먼저 만들고, 제목 확정에 필요한 값만 확인한다.

## 주요 변화

`주요 변화` 속성에는 **게임 사이클과 관련이 큰 순서로 최대 4개의 작업 제목**을 한 줄에 하나씩 나열한다.

- 현재 프로젝트의 플레이 흐름과 집계 대상 작업의 직접적인 연결 정도로 정렬한다. 플레이 진행을 가능하게 하는 기능, 흐름을 막는 문제 해결, 실제 사이클 연결·검증을 우선하고, 이를 보조하는 표현·도구·문서 작업은 뒤에 둔다. 시간순, 커밋순, 작업량순으로 나열하지 않는다.
- 예를 들어 상호작용·스캔·해킹·해금이 현재 사이클이면 그 흐름에 기여하는 작업을 우선한다. 이 예시를 프로젝트의 고정 사이클이나 반드시 채워야 하는 항목으로 사용하지 않는다.
- `스캔 GAS 입력 연결`, `해킹 셀 전파 규칙 설계`처럼 대상과 한 일이 드러나는 제목형 명사구로 쓴다. 설명 문장, 성과 평가, 괄호 속 부연은 상세 본문에 둔다.
- 같은 작업의 세부 변경은 묶고, 서로 다른 일을 한 줄에 몰아 넣어 4개 제한을 우회하지 않는다. 1~3개면 그대로 쓰며, 채울 근거가 없으면 빈칸으로 둔다.

## 확인·남은 일

기존 템플릿의 **하나의 속성 `확인·남은 일`**을 그대로 사용한다. 사용자가 이 항목에 넣으라고 별도로 요청한 내용만 쓴다.

- 요청이 없는 새 보고에서는 비워 둔다. `없음`, `해당 없음`, 추정한 후속 작업이나 일반적인 검증 목록도 자동으로 넣지 않는다.
- 전날의 미완료 항목, 코드에서 발견한 미검증 사항, 일반적인 PIE·빌드·P4 확인 사항을 자동 이월하지 않는다. 본문의 별도 남은 일 목록으로 우회하여 추가하지도 않는다.
- 기존 보고의 일부를 수정하는 요청이면 범위 밖의 기존 속성값은 유지한다. 사용자가 이 속성을 다시 작성하거나 비우라고 요청한 경우에만 그 범위대로 변경한다.
- 본문에서는 실제 수행한 작업과 검증 범위를 정확히 적되, 이를 근거로 요청하지 않은 다음 할 일을 만들어내지 않는다.

## 기존 템플릿과 상세 본문

가능하면 프로젝트 Notion에서 해당 작성자의 최근 보고 한 건을 열어 속성 이름·순서·본문 모양을 확인한다. 형식 참고용 보고의 내용을 오늘 작업으로 재사용하지 않는다.

기본 속성 순서는 `관련 업무 → 기간 → 작성자 → 종류 → 주요 변화 → 확인·남은 일`이다. `작성자`는 위에서 확인한 보고 작성자, `종류`는 기존 값인 `일일`을 사용한다. 관련 업무는 근거 있는 기존 관계만 연결하며, 알 수 없는 관계는 만들어 넣지 않는다.

상세 본문은 **작업별 짧은 제목 + 해당 작업 설명**을 유지한다. 설명은 기존 보고처럼 담백한 문장으로 쓰며 보통 1~2문장이면 충분하다. `주요 변화`의 4개 제한은 상세 본문 전체에 적용하지 않는다. 본문 항목 수도 이전 보고의 10개·11개 등에 맞춰 억지로 채우지 않는다.

초안을 채팅으로 전달할 때도 속성과 본문을 구분하고, 비어 있는 `확인·남은 일`에는 내용을 채우지 않는다. 윤문 점수나 작성 과정 설명을 보고 안에 넣지 않는다.

## Notion 작업

프로젝트의 Notion 조회·검색·작성·수정·관계 연결·저장 확인은 **로그인된 브라우저 UI만** 사용한다. Notion API·MCP·커넥터로 대체하지 않는다. 로그인이나 접근이 막히면 이미 제공된 자료로 초안을 만들고 확인할 수 없는 부분만 밝힌다.

**일일보고 작성·수정 요청의 기본 결과물은 Notion에 저장된 보고다.** 사용자가 별도로 Notion 반영을 말하지 않아도, 작성 요청에 해당 보고의 생성·수정이 포함된 것으로 보고 바로 반영한다.

- 같은 작성자·같은 날짜의 기존 보고가 있으면 해당 페이지와 속성을 갱신하고 제목 번호를 유지한다. 없으면 기존 일일·주간보고 데이터베이스에 새 보고를 만든다.
- 사용자가 명시적으로 `초안만`, `채팅으로만`, `Notion에는 반영하지 마`라고 요청한 경우에는 그 범위대로 채팅에만 전달한다.
- 반영 후 페이지를 다시 열거나 새로고침해 제목·날짜·주요 변화·본문을 UI로 확인하고, 보고 링크와 실제로 확인한 저장 상태를 전달한다.

마지막으로 집계 기간의 경계와 주말 이월이 맞는지, 주요 변화가 최대 4개의 제목인지, 게임 사이클 관련 순서인지, 요청하지 않은 확인·남은 일이 없는지, 제목 번호가 실제 작성 이력을 따르는지 대조한다.
