# 할 일 카드 작성

카드마다 최초 설계 단위, 구현 중 겪은 문제와 해결법, 실제 구현 내용을 아래의 세 구역으로 작성한다. 한국어로 짧고 구체적으로 쓴다.

## 자료와 카드 범위

- 현재 대화, 사용자가 지정한 설계 문서·작업 기록, 기존 카드, 필요한 관련 코드와 검증 결과에서 근거를 확인한다. `reviewed-feature-guide` 등으로 정리한 개발 단위가 있으면 그 목록을 사용한다.
- 각 카드에 해당하는 설계 단위와 구현 내용만 넣는다. 여러 카드를 요청하면 카드별로 같은 형식을 반복한다.
- 최초 설계 단위의 이름·순서·범위를 유지한다. 사용자가 승인한 변경이 있으면 반영하고 변경 사실을 짧게 남긴다. 설명 편의를 위해 단위를 임의로 합치거나 새로 쪼개지 않는다.
- 최초 설계 단위나 대상 카드를 특정할 수 없으면 제공된 자료와 프로젝트 Notion을 먼저 확인하고, 그래도 부족한 정보만 묻는다. 일반적인 준비·구현·테스트 항목으로 설계 단위를 대신하지 않는다.

## 카드 본문

아래 형식에서 대괄호 안의 설명을 실제 내용으로 바꾼다. 본문에는 세 구역과 그 사이 구분선 두 개를 사용한다. 항목 수는 실제 설계와 기록에 맞춘다.

```markdown
## 설계 단위

- [ ] [최초 설계 단위 이름]
- [x] [완료가 확인된 설계 단위 이름]

---

## 문제와 해결법

- [문제 또는 증상] → [해결 방법과 확인된 결과]

---

## 구현 내용

- [이 카드에서 구현한 기능과 달라진 동작]
```

### 설계 단위 체크리스트

한 설계 단위를 체크항목 하나로 쓴다. 해당 단위의 완료 기준을 충족한 근거가 있을 때만 체크한다. 설명·계획·예시 제공을 구현 완료로 표시하지 않는다. 코드 반영, 빌드, Blueprint 연결, 실행 검증은 확인된 범위를 구분하고, 필요한 검증이 남으면 체크하지 않은 채 항목 뒤에 짧게 적는다.

### 문제와 해결법

구현 중 실제 발생한 문제마다 증상과 해결법을 보통 한 줄로 요약한다. 원인은 확인된 경우에만 넣는다. 해결이 확인되지 않았으면 `미해결 — 현재 확인된 내용`으로 쓰고, 제안한 해결법을 완료한 조치처럼 쓰지 않는다. 자료에 문제 기록이 없으면 `기록된 문제 없음`으로 적는다.

### 구현 내용

이 카드에서 실제 구현한 기능과 동작 변화를 짧게 요약한다. 체크리스트를 그대로 복사하기보다 무엇이 가능해졌는지 설명한다. 이해에 필요한 클래스·함수·애셋 이름은 유지한다. 아직 구현하지 않은 계획은 구현 결과에 섞지 않는다. 미구현이 확인되면 `아직 구현한 내용 없음`, 확인 자료가 부족하면 `구현 내용 확인 필요`로 적는다.

## Notion 저장

**작성·수정 요청의 기본 결과물은 프로젝트 Notion에 저장된 할 일 카드다.** 이미 받은 작성 요청에 따라 바로 반영하며, 사용자가 `초안만`, `채팅으로만`, `Notion에는 반영하지 마`라고 지정하면 그 범위로 제한한다.

1. Notion 조회·검색·작성·수정·연결·저장 확인은 로그인된 브라우저 UI로 수행한다. Notion API·MCP·커넥터를 사용하지 않는다.
2. 사용자가 지정한 카드 또는 같은 작업의 기존 카드를 먼저 찾아 갱신한다. 없으면 프로젝트의 기존 할 일 데이터베이스에 만든다. 대상이 여러 개라 특정할 수 없으면 필요한 위치만 확인한다.
3. Notion에서는 체크리스트를 실제 할 일 블록으로, 두 구분선을 실제 구분선 블록으로 만든다. 페이지 제목은 작업명이 드러나게 쓰고, 기존 속성·관계·요청 범위 밖의 내용은 보존한다.
4. 저장 후 카드를 다시 열거나 새로고침하여 세 구역, 체크 상태, 구분선 두 개와 내용을 확인한다. 카드 링크와 실제로 확인한 저장 상태를 전달한다.

로그인이나 접근이 막히면 API로 우회하지 않는다. 확인한 자료로 초안을 제공하고 막힌 지점과 저장 여부를 알린다. 쓰기 후 확인만 막혔다면 재확인 불가 상태를 밝히고 같은 카드를 중복 생성하지 않는다.
