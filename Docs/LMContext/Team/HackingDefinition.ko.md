# 해킹 퍼즐 데이터 에셋과 격자 편집기

퍼즐 설정을 `ULMHackingPuzzleData`로 저장하고, 에셋 상세 패널의 R×C 격자에서 초기 숫자를 직접 작성한다. 해킹 컴포넌트는 지정한 에셋을 세션 시작 시 복사한다.

## 코드와 에셋의 적용 순서

1. 에디터에서 작업을 저장하고 종료한다. 새 UCLASS·모듈은 전체 Editor 빌드로 반영한다.
2. 검증할 작업 브랜치의 코드를 받는다. 현재 작업에 미커밋 변경이 있으면 먼저 보존한다.
3. `Lumia.uproject`는 Perforce 소유다. P4V에서 Check Out한 뒤 아래 동반 패치를 적용한다. 원본 `.uproject`를 Git에 추가하지 않는다.

```powershell
git apply --check Docs/LMContext/Team/HackingEditor.uproject.patch
git apply Docs/LMContext/Team/HackingEditor.uproject.patch
```

`Modules`에 아래 항목이 이미 있으면 중복 적용하지 않는다. 다른 사유로 패치가 실패하면 기존 설정을 보존하고 이 항목만 추가한다. 이 등록이 없으면 DLL을 빌드해도 격자 편집기가 자동으로 시작되지 않는다.

```json
{
    "Name": "LMHackingEditor",
    "Type": "Editor",
    "LoadingPhase": "PostEngineInit"
}
```

4. 프로젝트 파일을 갱신하고 `LumiaEditor / Win64 / Development`를 빌드한 뒤 에디터를 실행한다. 빌드·UHT·BP 컴파일·PIE는 사용자가 수행한다.
5. Content Browser의 **우클릭 → Miscellaneous → Data Asset → LMHackingPuzzleData**로 에셋을 만든다. 이름은 `DA_LM_HackingTest`로 제안한다.
6. 에셋에서 행·열을 입력하고 **크기 적용**을 누른다. 숫자 배열이 비어 있으면 **격자 생성** 버튼으로 칸을 만든다. 배열 개수를 미리 설정할 필요는 없다. 생성된 격자 칸마다 `0~F`를 입력한다. `Available Values`, `Target Value`, `Max Moves`도 작성한다. 기본 숫자 필드에서 F는 15다.
7. 기존 액터의 LMHacking 컴포넌트에 남아 있는 **이전 퍼즐 설정**을 참고해 해당 설정을 에셋으로 옮기고 저장한다. 클래스 기본값과 개별 인스턴스 오버라이드를 각각 확인한다.
8. 해당 컴포넌트의 **Puzzle Data**에 만든 에셋을 지정한다. 공통 설정은 BP 기본값, 다른 설정은 인스턴스에서 지정한다. 에셋/BP/맵 변경은 Perforce에서 관리한다.

기존 `Definition`은 이전 값의 보존을 위해 이름·타입·직렬화를 유지한다. 읽기 전용이고 게임에서는 사용하지 않는다. 별도의 `ActiveDefinition`만 일시적인 세션 설정으로 사용한다. `Puzzle Data`가 비어 있으면 이전 값으로 실행하지 않고 시작을 거부한다. 이전용 프로퍼티는 모든 기존 에셋의 이전 확인 후 별도 변경에서 제거할 수 있다.

## 편집 동작

- 좌표는 0부터 시작한다. 저장 인덱스는 `Row * Cols + Column`이다.
- 크기는 버튼을 눌러야 바뀐다. 겹치는 좌표의 값은 보존하고 새 칸은 0으로 채운다. 축소 시 범위 밖 값은 제거되며 Undo로 복구할 수 있다.
- 한 칸 수정과 크기 변경은 언리얼 속성 시스템의 Undo/Redo·저장을 사용한다. 에셋을 열기만 해서는 변경하지 않는다.
- 숫자는 한 자리 `0~F`이며 소문자도 허용한다. 빈 값이나 `G`, `10`, `0xF`는 저장하지 않는다.
- 격자 직접 편집은 축당 64 이하, 총 1024칸 이하에서 제공한다. 이는 Slate 화면 크기 제한이며 런타임 퍼즐 크기 제한이 아니다. 빈 배열은 격자 생성 화면을 제공한다. 범위 초과·값이 있는 배열의 잘못된 길이·다중 선택은 기본 속성 화면을 제공하고 원본을 자동 축소하지 않는다.
- `ResultText`, 완료 태그, 상호작용 연결은 기존 액터/컴포넌트에 유지한다. 기존 HUD 이벤트·Cell 전파·재시도 경로를 사용한다.

## 사용자 검증

### 격자와 저장

1. 2×3 격자에 `[0 1 2 / 3 4 5]`를 작성한다.
2. 3×4로 늘리면 `[0 1 2 0 / 3 4 5 0 / 0 0 0 0]`이어야 한다.
3. Undo/Redo로 크기와 값이 함께 돌아오는지 확인한다. 원본 2×3에서 2×2로 줄이면 `[0 1 / 3 4]`여야 한다.
4. 셀 수정도 Undo/Redo하고, 저장·닫기·다시 열기 후 값과 크기를 확인한다.
5. `F`, `f`, `0`을 입력하고 잘못된 값과 빈 값은 기존 숫자를 덮어쓰지 않는지 확인한다.
6. 두 에셋 선택, 배열 길이가 잘못된 에셋, 큰 에셋의 기본 편집기 전환에서 원본이 바뀌지 않는지 확인한다.
7. 행·열이 2×2이고 초기 숫자 배열이 비어 있는 에셋은 **격자 생성**을 누르면 0 네 칸이 나타나야 한다. 각 칸에 값을 입력하고 Undo/Redo·저장·재열기를 확인한다.

### 게임 적용

1. NeedHacking 액터에 `Rows=2`, `Cols=2`, 초기값 `[1,1,1,15]`, 선택값 `[15]`, 목표15, 최대1인 에셋을 지정한다.
2. 상호작용하면 기존 HUD에 2×2 `[1 1 / 1 F]`와 선택 숫자 F, 남은 횟수1이 나와야 한다.
3. 성공 전에 닫고 다시 열어 초기 설정을 확인한다. 클릭·성공·확인 닫기는 기존 연결대로 작동해야 한다.
4. 같은 에셋을 참조하는 두 액터의 진행이 독립적이고 원본 에셋 값이 유지되는지 확인한다.
5. Puzzle Data=None 또는 2×2/초기값3개인 별도 시험 에셋은 경고를 남기고 UI·새 일시정지로 진입하지 않아야 한다.
6. 실패 후 기존 RetryPuzzle 경로는 이번 세션의 초기 숫자와 횟수를 복원해야 한다.

### 실패 후 재시도

`WBP_LM_HackingPuzzle`의 `BTN_Retry`는 실패 상태에서만 표시한다. 비활성화되는 격자·팔레트 밖의 `VerticalBox_134`에 배치하고, 기본 Visibility는 Collapsed로 둔다.

- `On Clicked (BTN_Retry)` → `RequestRetry` → 기존 컴포넌트의 `RetryPuzzle`.
- `OnPuzzleUpdated` 공통 진입에서 `Phase == Failed`이면 Visible, 나머지는 Collapsed로 갱신한다.
- 컴포넌트가 초기 셀 값과 사용 횟수를 복원한 뒤 Playing으로 전환하고 갱신 이벤트를 보낸다. 기존 Playing 비교가 격자·팔레트를 다시 활성화한다.
- 선택 숫자, 현재 화면, 일시정지와 UIOnly 입력은 유지한다. 위젯 재생성이나 닫기·상호작용 종료를 호출하지 않는다.

사용자는 WBP를 컴파일한 뒤 실패 → 재시도 → 초기 숫자·남은 횟수 복원 → 다시 클릭의 흐름을 확인한다. 재시도 후 버튼 숨김, 선택 색 유지, 반복 재시도, 닫기, 성공 화면에서 버튼 숨김도 확인한다. WBP는 Perforce 소유이므로 Git 코드와 함께 별도로 반영해야 한다.

### 선택 실행할 자동화 검사

작성된 검사는 좌표 보존 크기 변경과 숫자 파싱을 확인한다. 여기서 실행 완료를 의미하지 않는다.

```text
Automation RunTests Lumia.Hacking.Definition
```

이 검사는 Slate 화면의 실제 조작·저장·Undo 및 게임 상호작용 검사를 대신하지 않는다. 에디터 의존성은 `LMHackingEditor`에만 있으며 일반 게임 타깃에는 추가하지 않았다. 실제 패키징 검증은 별도로 수행한다.

## 변경 구성

- `Source/Lumia/Public/Hacking/LMHackingPuzzleData.h`: 퍼즐 원본 에셋.
- `LMHackingComponent`: 필수 에셋 참조·세션 복사본·이전 설정 보존.
- `Source/LMHackingEditor`: 격자 상세 패널, 편집 계산, 자동화 검사.
- `Source/LumiaEditor.Target.cs`: 에디터 빌드 모듈 추가.
- `HackingEditor.uproject.patch`: Perforce 소유 프로젝트 설명 파일의 동반 변경.

PR은 사용자 검증을 받은 뒤 작성한다. 이 안내에는 빌드·UHT·PIE·패키징 통과를 기록하지 않는다.
